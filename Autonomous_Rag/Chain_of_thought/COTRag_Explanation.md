# COT RAG — How the Code Works

## What is COT RAG?

COT RAG combines two ideas:

- **RAG (Retrieval Augmented Generation)** — fetch relevant documents from a knowledge base before answering, so the LLM uses real information instead of its own training knowledge
- **COT (Chain of Thought)** — force the LLM to reason through a problem step by step before giving a final answer, instead of jumping straight to a conclusion

Together they produce answers that are both **grounded in your documents** and **reasoned through carefully**.

---

## The Pipeline — 3 Stages

```
User Question
      │
      ▼
┌─────────────┐
│  retriever  │  Step 1 — Find relevant chunks from vectorstore
└─────────────┘
      │
      ▼
┌─────────────┐
│   planner   │  Step 2 — Break question into reasoning steps using retrieved context
└─────────────┘
      │
      ▼
┌─────────────┐
│  responder  │  Step 3 — Reason through each step and generate final answer
└─────────────┘
      │
      ▼
  Final Answer
```

---

## State — What Gets Passed Between Stages

```python
class RAGCoTState(BaseModel):
    question:       str             # the original user question — never changes
    sub_steps:      List[str] = []  # reasoning steps generated by planner
    retrieved_docs: List[Document] = []  # chunks retrieved from vectorstore
    answer:         str = ""        # final answer produced by responder
```

This state object travels through all three nodes. Each node reads from it and writes back to it using `model_copy(update={...})`.

---

## Stage 1 — `retrieve_per_step` (retriever node)

**Runs first. Uses the original question to fetch relevant document chunks.**

```python
def retrieve_per_step(state: RAGCoTState) -> RAGCoTState:
    THRESHOLD = 0.30   # minimum relevance score to keep a chunk
    K = 5              # number of chunks to return
    FETCH_K = 20       # larger pool MMR selects from
    LAMBDA_MULT = 0.6  # balance between relevance and diversity

    docs_with_scores = vectorstore.similarity_search_with_relevance_scores(
        state.question,   # always the original question at this stage
        k=K,
        search_type="mmr",
        search_kwargs={"fetch_k": FETCH_K, "lambda_mult": LAMBDA_MULT}
    )

    filtered = [
        doc for doc, score in docs_with_scores
        if score >= THRESHOLD    # only keep chunks above threshold
    ]
    return state.model_copy(update={"retrieved_docs": filtered})
```

### What happens here

- Uses **MMR (Maximal Marginal Relevance)** retrieval — fetches 20 candidate chunks, then picks the 5 that are both relevant AND diverse (avoids returning 5 near-identical chunks)
- Filters by **threshold 0.30** — any chunk with a relevance score below 0.30 is discarded
- If nothing passes the threshold, `retrieved_docs` stays empty and `generate_answer` will return "I could not find relevant information" instead of hallucinating

### Why retrieve before planning?

The planner runs **after** retrieval so it can see the actual document content before generating reasoning steps. This prevents the LLM from generating generic steps based on its own training knowledge instead of your specific documents.

```
STATE AFTER retriever:
  question:       "what are metaphor prompt approaches?"
  sub_steps:      []                          ← still empty
  retrieved_docs: [Chunk1, Chunk2, Chunk3]    ← populated ✅
  answer:         ""
```

## Stage 2 — `plan_steps` (planner node)

**Uses the retrieved context to generate grounded reasoning steps.**

```python
def plan_steps(state: RAGCoTState) -> RAGCoTState:
    context = "\n\n".join(doc.page_content for doc in state.retrieved_docs)

    prompt = f"""Given this retrieved context from a research paper:

{context}

Break the following question into 2-3 reasoning steps 
that can be answered using ONLY the context above:

Question: {state.question}"""

    result = llm.invoke(prompt).content
    subqs = [line.strip("- ") for line in result.split("\n") if line.strip()]
    return state.model_copy(update={"sub_steps": subqs})
```

### What happens here

- Passes the **already-retrieved context** into the prompt so the LLM generates steps grounded in your documents
- The LLM produces 2-3 reasoning steps as a numbered list
- Each line is stripped of bullet/dash markers and stored in `sub_steps`

### Why this matters

Without passing the retrieved context here, the LLM would generate generic steps from its own training knowledge. For example:

```
❌ Without context (generic GPT-4o knowledge):
   Step 1: Understand baseline Transformer benchmarks like GLUE, SuperGLUE
   Step 2: Identify gaps in standard evaluation methods
   Step 3: Design additional experiments...
   → Completely ignores your paper

✅ With context (grounded in your document):
   Step 1: Identify the metaphor prompt approaches described in the paper
   Step 2: Understand how analogical reasoning is applied in each approach
   Step 3: Compare the performance metrics across approaches
   → Directly answers from your paper's content
```

```
STATE AFTER planner:
  question:       "what are metaphor prompt approaches?"
  sub_steps:      ["Step 1: Identify...", "Step 2: Understand...", "Step 3: Compare..."]
  retrieved_docs: [Chunk1, Chunk2, Chunk3]    ← unchanged
  answer:         ""
```

## Stage 3 — `generate_answer` (responder node)

**Reasons through each step using the retrieved evidence, then synthesises a final answer.**

```python
def generate_answer(state: RAGCoTState) -> RAGCoTState:

    # Guard — if retrieval found nothing, say so honestly
    if not state.retrieved_docs:
        return state.model_copy(update={
            "answer": "I could not find relevant information in the knowledge base to answer this question."
        })

    context = "\n\n".join([doc.page_content for doc in state.retrieved_docs])

    prompt = f"""
You are answering a complex question using step-by-step reasoning.

Question: {state.question}

Reasoning steps to follow:
{chr(10).join(f"Step {i+1}: {step}" for i, step in enumerate(state.sub_steps))}

Retrieved evidence for each step:
{context}

Now work through each step one by one using the evidence above, 
then synthesize a final answer at the end.

Step 1 reasoning:
Step 2 reasoning:
Step 3 reasoning:
Final Answer:
"""
    result = llm.invoke(prompt).content.strip()
    return state.model_copy(update={"answer": result})
```

### What happens here

- First checks if `retrieved_docs` is empty — if so, returns an honest "no information found" message without calling the LLM at all
- Builds a structured prompt that includes the original question, the reasoning steps from the planner, and the retrieved evidence
- The prompt template with `Step 1 reasoning:`, `Step 2 reasoning:`, `Final Answer:` forces the LLM to reason explicitly through each step before concluding — this is the COT part
- Without these explicit step headers the LLM would skip straight to a conclusion

```
STATE AFTER responder (FINAL):
  question:       "what are metaphor prompt approaches?"
  sub_steps:      ["Step 1...", "Step 2...", "Step 3..."]
  retrieved_docs: [Chunk1, Chunk2, Chunk3]
  answer:         "Step 1 reasoning: The paper describes...
                   Step 2 reasoning: Analogical reasoning is applied by...
                   Final Answer: The metaphor prompt approaches include..."
```

## Key Design Decisions

**Retrieve before plan** — the retriever runs first so the planner has real document content to work with. If the planner ran first it would generate generic steps from GPT-4o's own knowledge, not from your documents.

**Threshold filtering** — chunks below 0.30 relevance are discarded before reaching the LLM. This prevents the LLM from using irrelevant content and making up answers to fill the gap.

**Empty retrieval guard** — if no chunks pass the threshold, the pipeline returns an honest message instead of letting GPT-4o hallucinate an answer from its training data.

**COT in the prompt, not in the graph** — chain of thought is implemented entirely inside the `generate_answer` prompt by providing explicit step headers (`Step 1 reasoning:`, `Final Answer:`). The graph structure itself doesn't change — it is a single linear pass.

## Comparison with Rewrite Query Agent

| Feature | COTRag | Rewrite Query Agent |
|---|---|---|
| Decomposition | Reasoning steps for COT | Independent retrieval queries |
| Retrieval | Single pass, original question | One tool call per sub-question |
| Grading | ❌ No | ✅ Yes — pass/fail per sub-question |
| Retry on failure | ❌ No | ✅ Yes — up to MAX_REWRITES |
| Graph complexity | Simple linear — 3 nodes | Full loop — 6 nodes |
| Best for | Deep reasoning on one topic | Multi-part questions across sources |
